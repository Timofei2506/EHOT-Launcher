# CI — что это и зачем (объяснение «на пальцах»)

CI (Continuous Integration, «непрерывная интеграция») — это робот на GitHub, который сам проверяет твой код
после каждого изменения. Тебе не нужно помнить команды: залил изменения → робот собрал → робот прогнал тесты →
показал зелёный крестик или красный.

## Что настроено

Файл: `.github/workflows/ci.yml`. Запускается на каждый `push` в `main` и на каждый pull request,
а также вручную (вкладка **Actions** → **CI** → **Run workflow**).

### Работа 1 — «Сборка и тесты»
Одновременно на трёх системах: Ubuntu, Windows, macOS.
1. Ставит .NET 10.
2. `dotnet restore` — скачивает зависимости.
3. `dotnet build -warnaserror` — собирает. **Важно:** сборка падает, если появилось хоть одно предупреждение,
   поэтому «мусор» в коде не накапливается.
4. `dotnet test` — прогоняет все тесты (сейчас 43: 35 логических + 8 UI-тестов без экрана).
5. Складывает отчёт `results.trx` в Artifacts.

### Работа 2 — «Сборка приложения»
Стартует только если первая работа прошла. Собирает готовые к запуску папки и упаковывает в zip:
- `win-x64` — Windows 64-бит;
- `osx-arm64` — macOS на Apple Silicon (M1/M2/M3/M4);
- `osx-x64` — macOS на Intel.

`.NET` уже внутри (`--self-contained`), пользователю ничего доустанавливать не нужно.
Архивы лежат в **Actions → нужный запуск → Artifacts**.

## Как читать результат

- 🟢 зелёная галочка — всё собралось и все тесты прошли.
- 🔴 красный крестик — что-то сломалось. Открываешь запуск → нужную систему → шаг с красным крестом,
  там будет текст ошибки. Именно эти строки нужно показать мне (или вставить в чат), чтобы я починил.

## Чего CI не делает (пока)

- Не подписывает приложение (Windows EV-сертификат, Apple Developer ID) — это требует платных сертификатов
  и секретов репозитория.
- Не делает установщики (Inno Setup `.exe`, `.dmg`) — они на этапе 8.
- Не публикует в Microsoft Store / не хостит relay-сервер для Game Network.

## Локально vs CI

| Действие | Локально | В CI |
| --- | --- | --- |
| Собрать | `dotnet build EHOT.Launcher.slnx` | автоматически |
| Тесты | `bash scripts/build.sh test` | автоматически |
| Сборка под платформу | `bash scripts/build.sh publish win` | автоматически, сразу под 3 платформы |

Если CI красный, а локально всё зелёное — чаще всего дело в разнице систем (регистр букв в путях на Linux,
разделители путей, отсутствующий файл, который «случайно» не попал в git).

## Установщики (этап 8)

Третья работа CI — `Установщик`. Она собирает не папку, а готовые к установке файлы:

| Платформа | Как собирается | Что получается |
| --- | --- | --- |
| Windows | Inno Setup 6 (`packaging/windows/ehot-launcher.iss`) | `EHOT-Launcher-<версия>-win-x64-setup.exe` |
| macOS (Apple Silicon / Intel) | `packaging/macos/make-dmg.sh` | `EHOT-Launcher-<версия>-osx-arm64.dmg`, `…-osx-x64.dmg` |

Что делает установщик Windows:
- ставит приложение в `Program Files\EHOT Launcher`, создаёт ярлык в меню «Пуск» и (по желанию) на рабочем столе;
- показывает лицензию, корректно удаляется через «Приложения и возможности»;
- регистрирует протокол `ehot://` — ссылка-приглашение из браузера открывает лаунчер и подставляет код комнаты.

Что делает `.dmg`:
- внутри `.app` с иконкой и `Info.plist` (`app.ehot.launcher`, минимум macOS 11);
- при открытии образа рядом с приложением лежит ярлык **Applications** — перетащил и готово;
- в CI делается ad-hoc подпись (`codesign -s -`), чтобы приложение запускалось на своей машине.
  Для распространения без предупреждений нужен Apple Developer ID + нотаризация.

Проверить локально (нужен Windows + Inno Setup):

```
iscc.exe packaging\windows\ehot-launcher.iss /DAppVersion=0.1.0 /DSourceDir=<папка publish> /DOutputDir=<куда положить>
```
